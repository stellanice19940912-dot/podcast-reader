一句话概述

大卫·翁德雷（David Ondrej）认为，很多人电脑上装着几百个智能体技能（agent skills），真正常用的大概只有五六个——多半是从推特（Twitter）、YouTube 上周周爆红的仓库里盲拷来的。堆技能会浪费大量 token、更快撞上用量上限，还会拖累智能体表现；抄爆款却不知其所以然，本身就是「不会用 AI」的信号。他主张当天删掉 80% 到 90% 不怎么用的技能，只留下真正匹配自己工作流的少数几个，并演示了他每天在用的五个：GPT review、Deep API、State、Stop overthinking，以及设计预览（show me designs）。技能格式由 Anthropic 在去年创建、今年爆发，是开放标准；它比单条提示词高一层，是整套工作流——平时只加载描述，调用时才加载正文。

核心要点

  • 盲拷很危险：有个打着安德烈·卡帕西（Andrej Karpathy）旗号的技能仓库，其实是路人根据推文脑补出来的，属于营销笑话。技能一多，每条描述都会打进每一条消息，像「千刀万剐」一样吃掉上下文；五到二十个还好，超过五十个就可能把你毁掉。描述写得很宽时还会被频繁触发，把整段正文灌进窗口，逼你不断 /compact，甚至去买第二、第三、第四份订阅——其实只是 token 优化问题。别人的日常（包括他自己或马特·PCO（Matt PCO）的公开仓库）和你的工作流重合的概率大约是 0%。
  • 他做 AI 内容四年以上，亲手做了 200 甚至 300 多个技能，每天用 6、8、10 个小时，超过 95% 是针对具体问题原创的。公开技能仓库免费开源（片中显示大约 4000 star），但他只建议拿走其中两三个、最多四个真正相关的，不要整库克隆——哪怕这对他「拉人进自己的生态」更有利。2024 年看谁会用 AI，看的是有没有付费套餐；2026 年他觉得关键指标变成：你多久能为自己的流程写出一个技能。能在重复工作开始之前就动手写技能的人，通常属于前 10%，甚至前 1% 到 2%。
  • 该抄的时候也要抄：他转发了 Cloudflare 的 security audit skill。在「黑色十月」（Black October）一类安全事件之后，用 Opus 5.5 或 GPT 6.1 Soul 等前沿模型配上靠谱技能去审计代码是合理的；Cloudflare 作为估值超过 1000 亿美元的公司，在网络安全上可信。他只在隔离的云沙箱里跑了一次，没有永久装上。不要从只有 50 个粉丝的路人那里拷技能，可能藏有提示注入（prompt injection），让智能体把文件传到网上；本地或开源的便宜模型更容易中招。标准目录是 agents/skills；Claude Code（Claude Code）过去坚持自己的 .claude/skills，大约一个多月前才兼容该标准，以前还得靠符号链接。
  • 删除方法：截一张他准备好的提示图，丢给 Opus 5.5 或最新的 GPT，用 high、extra high 或 max 跑，分析 Hermes、Pi、Codex、Claude Code、Cursor 等各套编排里最少用到的技能。分析本身不删除；删了随时能加回来。他自己即以 Opus 5.5 做主力、只用 GPT 做审查，也快撞上 OpenAI 200 美元套餐的额度。不要一次删光，删掉最少用的 80% 到 90% 即可，你会惊讶日常几乎没什么变化，只是不那么容易撞上限。
  • 五个他每天（或几乎每天）在用的技能：GPT review——用另一家前沿厂商的模型（OpenAI 的编排，他现场用 Astra，并盼着 GPT 6.2 Astra 和 Soul）去审 Opus 5.5 做完的中大型改动，自称能抓出 95% 的 bug；改按钮大小颜色这类小事不必跑，一年前那种「每次 push 都跑全套 CI」在当前前沿模型下过时了。Deep API 把抓取、搜索、发邮件、深度研究收成一个接口，省掉 Firecrawl、Apify、AgentMail 等分散的账单和密钥，也补上模型的知识截止日期。State 用一两句英文问「我们在干什么、完成了百分之多少」。Stop overthinking 对抗模型「总能找出 bug」的偏见，避免为十亿分之一的边缘情况写 200 行测试。设计预览把高质量效果图直接渲在对话里，不必先起开发服务器；他强调别死等一条会话，至少同时开 5 到 10 条。
  • 技能是 AI 时代的标准作业程序（SOP）。贝索斯（Jeff Bezos）在 2016 年致股东信里说：「好流程为你服务，好让你服务客户。」专门技能（比如修计费 bug 时，支付服务商是谁、哪些 API 密钥绝对不能动）远优于「写更好的代码」这种空泛技能。他在 Cloudroom（Cloudroom）里常驻 32 条智能体循环，已经跑过 1.2 万次，并主张 90/10：90% 的时候征求你批准，10% 明显安全时可自动执行。云端智能体必须能带上你自己的技能配置；新手把一切做成全局技能，高手把大多数做成项目级技能。团队里该由最懂某件事的人（市场总监、财务总监，或最好的销售、缩略图设计师）把技能推进共享的 GitHub 仓库，新人一周内就能跟上，而不是几个月。

  1. 1开场：删掉 90% 的技能，别再盲抄爆款仓库查看原文 →

    大卫·翁德雷（David Ondrej）一上来就说：你现在大概该删掉 90% 的智能体技能。很多人电脑上装着几百个技能，真正常用的大约只有五六个，原因是在推特和 YouTube 上看到每周爆红的技能仓库就盲目复制，以为「能火就一定能让我变更强」。他声明自己并不反对技能，反对的是抄了却不会用、也不知道自己在用什么。他会讲自己用哪些技能、怎么写、该怎么用，以及什么时候从这些仓库里拿才合理——这些仓库并非全无价值。但反例很刺眼：有个打着安德烈·卡帕西（Andrej Karpathy）旗号的技能仓库，第一眼会觉得「世界级 AI 研究者亲自出品」，再看才发现根本不是他写的，而是一个路人根据一些推文去脑补「他可能会有什么技能」。这类东西就是营销笑话。

  2. 2技能是什么：描述与正文、上下文浪费，以及格式从哪来查看原文 →

    有些仓库确实有点价值，但关键是：目录被技能撑爆之后，你会浪费大量 token、更快撞上用量上限，还会伤害智能体的表现，而自己什么也没学到。盲抄爆款等于完全不知道发生了什么，这本身就是「你不擅长用 AI」的信号。本期他会示范当天怎样删掉 80% 到 90% 的技能并在结束时工作得更快，接着讲他每天在用的四五个技能，以及正确用法。技能是对某个流程的描述加上正文，比单条提示词高一层：提示词发一次就结束，技能可以是一连串提示、整套工作流。好处是正文通常更长，只在技能被调用时才加载，不至于一上来就吞掉整个上下文窗口。坏处是技能一多到几百个，光是描述就会变长；从爆款仓库盲拷来 300、400、500 个时，这些描述会打进每一条消息。五到十到二十个还好，超过五十个就可能把你毁掉。技能格式其实是 Anthropic 去年创建的开放标准，并非专有协议，几乎所有智能体今天都在遵循；到现在还不满一年，却在今年随着大家搞懂它是什么、怎么用而爆发。

  3. 3宽泛描述的陷阱，以及别人的工作流不可能刚好等于你的查看原文 →

    每个技能都需要描述加正文，它们都会进上下文。描述如果很窄——「我在修计费漏洞时再调用」——就很好；很多爆款技能的描述却写得很宽，结果被不停触发，不仅描述本身膨胀，整段正文也会灌进窗口。于是你频繁撞上上下文上限，不得不 /compact，甚至去买第二、第三、第四份订阅，其实并没有那么大的真实用量，只是遇到了 token 优化问题。盲拷最大的逻辑漏洞是：你每天起床后做的那一套具体工作，和马特·PCO（Matt PCO）、和他本人、或其他公开爆款仓库作者的日常，重合概率大约是 0%。因为你有自己的生意、自己的问题和自己的工作方式，从别人那里盲拷 50 个技能就是蠢。有人会问他有什么资格这么说：他做 AI 内容四年以上，访谈过智能体工程和技能领域里很硬的人，亲手做了 200 甚至 300 多个技能，每天用 6、8、10 个小时，其中超过 95% 是针对具体问题、从自己脑子里长出来的原创。他现在有一个完全免费开源的公开技能仓库，片中会给出链接，稍后也会说哪些值得考虑；但他反复强调，即便整库克隆在商业上对他更有利、能把人拉进自己的生态，他也不希望你盲目克隆——里面大概只有两三个、最多四个真正跟你的生活、生意和工作方式相关。

  4. 42026 年的水平指标：你多久能为自己写出一个技能查看原文 →

    他觉得，2024 年看一个人会不会用 AI，很大程度看有没有付费套餐——当时没有 ChatGPT 付费计划，基本就可以判断对方不在状态。到了 2026 年，他眼中几乎最重要的单一指标变成：你创造出一个技能要花多久。如果同样的智能体工作做了好几周才想到写技能，说明你还不算擅长；如果新工作流刚开始、你就已经预见到会重复、甚至在第一次做完之前就动手写技能，那你大概还不错。你为自己的流程写出多少独特技能，是你有多投入、有多站在 AI 前沿的重要代理指标。他在团队、朋友、家人和「新社会」（New Society）成员里都看到这一点：真正能讲清每个技能为什么存在、做什么、怎么运作的人——哪怕技能正文是让 AI 写的，大家都这么干——通常属于前 10%，甚至前 1% 到 2%。反过来，如果自定义技能很少，你大概还没那么会用 AI。

  5. 5什么时候该抄：Cloudflare 安全审计，以及 agents/skills 标准查看原文 →

    有时抄袭确实合理：仓库爆了，或对方明显比你更懂。他几天前转发了 Cloudflare 的 security audit skill，用来审计整个代码库的安全问题。大家都见过「黑色十月」（Black October）以及大量网络安全漏洞和利用；包括他自己在内，很多人并不是安全专家，所以应该用 Opus 5.5、GPT 6.1 Soul 或后续模型，配上靠谱技能去扫一遍代码。Cloudflare 作为估值超过 1000 亿美元的公司，在网络安全上高度可信，这就是他转发、也是大家产生共鸣的原因。但「跑一次」和「永远装上」是两回事：他只在隔离的云沙箱里启动云端智能体跑了一次。电脑上的标准目录是 agents/skills，现在连 Claude Code 也遵循。过去很长一段时间 Claude Code 只用 .claude/skills 文件夹——那个路径现在还能用——Anthropic 当时非常坚持自己的品味，并不接受 agents 标准，尽管这个格式某种程度上就是他们创的，一切都得带上 Claude 的烙印。直到大约一个多月、一个半月前，两边还得靠符号链接才能互通，因为 agents 目录里的东西不会加载进 Claude Code，只会被其他编排加载；现在好在 Claude Code 也会从 agents 加载。不要往这个受保护的目录里丢随机技能：如果不是来自 Cloudflare、他本人或 PCO，而是一个只有 50 个粉丝的路人，技能里可能有提示注入，让智能体把文件上传到网上。前沿模型也许不会上当，本地或开源的便宜模型却很容易中招。所以他强烈建议：第一，自己写技能；第二，若要拿别人的，确保对方是公众人物或会承担声誉代价的可信公司。

  6. 6怎么删：一条分析提示，先砍掉最少用的 80% 到 90%查看原文 →

    很多技能文件夹看起来像他演示的「Raptor one engine」那样：膨胀、零件太多、让人困惑。你应该追求的是功能清楚、好看、极简、优雅，只留真正在用的东西。他用一句话概括：在仍然有效的前提下，技能越少越好。加技能很容易——克隆仓库、再让智能体加 20 个——大多数人却从不删除，他自己也得提醒自己去删。他准备了一条提示：把屏幕上的图截下来，贴进你用的智能体（他更推荐 Cloudroom），用 Opus 5.5 或最新的 GPT 这类前沿模型，选 high、extra high 或 max 运行；如果认真做，他会用 max 去分析全部会话，片中演示用的是 high。智能体会检查 Hermes、Pi、Codex、Claude Code、Cursor 等各套编排的历史会话，找出你最少用到的技能，然后由你决定：十个里删光，还是留下两三个亲手打磨的「手作」技能。分析本身不删除任何东西，所以人人都该跑一遍，结果往往会让你震惊。删了随时能加回来，模型还在变强，重新生成或再去网上找并不难；真正有害的是天天把不用的技能留在目录里烧 token、更快撞上限。他自己即以 Opus 5.5 做主力、只用 GPT 做审查，也快撞上 OpenAI 200 美元套餐的额度——他顺便说 OpenAI 目前的用量限制并不理想，不过那是另一期的话题。他强调不要删光：删 80% 到 90%，把最少用的那一大截去掉；只删最少用的十个太保守。删完你会惊讶日常几乎没变化，只是不那么频繁撞上限。

  7. 7每天在用的技能之一：用另一家前沿模型做 GPT review查看原文 →

    删完之后他展示自己仍在用、也建议你考虑的五个技能。第一个是 GPT review。此时他认 Opus 5.5 是世界上最好的 AI 模型，或许新的 Anthropic 模型或新的开源模型以后会超越它，但眼下没有争论余地；它仍会像任何模型和任何人一样犯错。有人说「模型不完美、还会幻觉」，仿佛人类从不犯错，他觉得这种对比很蠢。他用 Opus 5.5 做完东西后，只需说「对这个跑一下 GPT review」、标记该技能即可。小事——改按钮大小、改某个界面元素颜色——不必跑；很多人对每一次推送都上疯狂的持续集成和审查，一年前这还算好主意，以现在的前沿模型则完全过头。他现场让技能检查过去大约 24 小时里对 Cloudroom 的提交：主智能体会在下方拉起一个子智能体去做审查。这种子智能体玩法基本上只在 Cloudroom 的云端会话里好用；他称 Cloudroom 是世上唯一在免费套餐里提供云端智能体的智能体开发环境（ADE），免费开源，可到 cloudroom.dev 下载，已支持 Windows，也能接 Claude Code、Cursor、Codex、Pi、Hermes、OpenCode、Kimi Droid 等本地和云端编排。演示里主智能体是 Claude Code 编排，子智能体是 Codex 编排，跑的是 Astra（他担心会撞上限，演示到一半停掉），推理档位是 fast 模式的 extra high，也可改。因为 Claude 来自 Anthropic，审查就该换另一家前沿编排：现在前沿编排基本上只有 OpenAI 和 Anthropic 两家，所以用最好的 GPT。他现场用的是 Astra，并盼着他们尽快放出 GPT 6.2 Astra 和 6.2 Soul，抱怨新模型迟迟不发布像是把用户当人质。用一家的前沿模型做完、再让另一家审一遍，他声称能抓住 95% 的缺陷，是真正的八二法则，他每天都用。

  8. 8Deep API 与 State：让智能体连上真实世界，并随时看清进度查看原文 →

    第二个每天都用的是 Deep API：给所有智能体提供一个统一接口，覆盖抓取、网络搜索、发邮件、深度研究等事情。否则你得分别接入 Firecrawl、Apify、AgentMail 等不同供应商，账单和 API 密钥都是分开的。它把各类最好的端点收在一起：最快的网络搜索、最好的深度研究、对推特和 GitHub 以及其他社交媒体最好的抓取，用来把智能体「锚定在现实和真相里」。即便是 Opus 或 GPT 这样的前沿模型也有知识截止日期，没有网络就没那么强；Codex 和 Claude Code 自带一些基础浏览，但不够好。原因是 OpenAI 和 Anthropic 已经是万亿美元级的大公司，不再是当初那种敢冒险的小创业公司，不会把最新、最激进的抓取能力交给你。所以他想让智能体拥有「最新火力」、在网上找到任何东西时，就用 Deep API。接下来是 State。他录像前刚重组过仓库，于是示范怎么找：下方链接的 GitHub skills 仓库（落地页大约 4000 star）打开 skills 文件夹，用 Command+F 搜 state。整个正文很短，就是一段英文：提醒我这条会话在做什么、完成了百分之多少，用简短朴素的英语极简回答。他开玩笑说大多数技能其实是 AI 写的，但这一条短而有效，看得出像手写。他在 Cloudroom 里每天跑上百条会话时会说「give state」，模型就会回报：比如正在用 GPT 审查已合并的改动、进度大约 15%，以及还剩什么、为什么要做。这个他一天用几次，频率不如前两个。

我前面简单提过，什么时候该写技能？如果你经常在做这件事，它是重复的流程；或者你觉得以后会常常做。比如你在做一个新项目，心想：我大概会反复做这种修订、这种设计、这种核算或重构，那就该写一个技能，把你想嵌入的东西写进去。

你希望知识被嵌进去，让智能体每次做那件事时都知道该怎么做。你对那个具体流程、具体工作流有自己的偏好和做法，希望智能体遵循——这时就该写技能。

我还想说，专门技能其实会打败宽泛技能。很多技能在描述和正文里都写得很宽，比如「更好的代码」。那到底是什么意思？「更好的代码」什么都可以指。专门技能则像我前面说的：我们在修一个跟计费有关的缺陷。计费很敏感。我们用的支付服务商是这个；这块绝对不能动；密钥在这里，只读。当技能足够专门时，你可以放进许多只在那种情境下才有意义的细节——那种情境也许只占你工作的 0.2%。

但当那 0.2% 到来时，智能体基本上能自己完成。这也就通向智能体循环的概念：智能体能够完全自动地做完你的工作。当你写下专门、高质量的技能，你才会有那种信心：好，我这 1%、这 2% 的工作，智能体每次都能完美拿下。然后你就可以为它建一条智能体循环。

在 Cloudroom 里，我们有一个叫 Loops 的功能，用来非常方便地创建和管理智能体循环。我现在常驻跑着 32 条循环，它们已经运行了 1.2 万次，由此省下的时间想一想都疯狂。我用的那些循环模板也可以一键加到你的仓库里。这些都在 Cloudroom 里，去 cloudroom.dev 安装即可。

还有一个叫 scan 的功能，原理其实一样：你应该只建立自己会用到的循环，就像我一直在讲的技能一样。它会扫描你电脑上所有本地的智能体会话，看你在做什么、怎么工作、有哪些重复习惯，以及该怎样为它们写技能，并拆成 90/10：90% 的时候它征求你批准并等你；10% 最明显、安全、可预测时，它就自己执行。

这才是生产率能进入指数区的地方，因为智能体在为你交付端到端的结果。它们不是只开一个任务或开一段研究，而是按你想要的方式，自主做完整套工作流。所以你该写高度专门的技能，也该建高度专门的智能体循环。

下一个概念：你的技能也应该能在云端智能体上工作。很多人之所以不拥抱云端，是因为他们的整套配置都在本地——所有技能、MCP、API、GitHub 仓库、项目都在本地，云上没有。问题是，市面上很多云功能和云端智能体方案，并不能很好地访问你的 MacBook。

我可以在这条云端会话里说：列出你现在拥有的全部技能。我们还能问得可爱一点：顺便说，我们在哪台电脑上？告诉我我们在哪台机器上。我是想确认它是在我的 MacBook 上，还是在云里——如果是在我的 MacBook 上，那这就是假演示。

重点是，你得真正拥抱云端智能体。我之前专门做过一期很详细的视频，缩略图我放在屏幕上。超短版就是：即便 MacBook 合上，智能体也能继续跑。它们不耗电、不占资源，也没有电脑操控（computer use）那种扰人的弹窗。不管你在不在网上，不管有没有无线网，它们都能继续跑。

所以云端智能体显然是未来。但很多人迟迟不采用，是因为他们缺少自己的那套配置和自己的技能。我示范一下我们怎么解决。先看第一条提示：这些是我现在拥有的全部技能，Cloudroom 的产品工程等等，你能看到这么多不同的技能。

然后我们在一个云沙箱里，它给出了沙箱信息。从左侧图标也能看出来，这不是跑在我自己的电脑上，而是跑在云端智能体沙箱里——它却仍然拥有我全部的技能。怎么做到的？因为我们把这件事做成了 Cloudroom 里的功能。

你点左下角的设置。顺便说，这里也会显示分析，非常好看：你能看到自己到底有多常用这些技能，哪些技能用得多、用得多勤，可视化很清楚。这些是我最常用的，你们可以暂停下来分析。

但我真正想给你们看的是云端配置。点进这里的 Cloud，你可以选择每次打开沙箱时要加载哪些技能。这些技能会在每一个新沙箱启动时被加载进去，所以你跑起来、打开它的时候，这些技能都已经在沙箱里了。你不必复制粘贴技能，也不必担心技能在不在。

而且你可以直接让智能体帮你配置，因为我设计 Cloudroom 的方式就是可被命令行控制：智能体可以通过命令行做所有事，你用英语跟它说话就行。我的重点是：如果你把云环境配置对了，就能像我这样，在云端会话里拥有全部技能，让云端智能体和本地一样强。这对 2027、2028 年的工程方式至关重要。云端智能体对很多人和公司都会非常重要；这一点对不少人是显然的，但很多人仍没有真正全面采用，因为他们缺少自己的技能、配置和仓库。我们正尽可能用 Cloudroom 解决这些问题。

接下来是全局技能和项目技能。全局技能适用于每一次聊天会话，永远会被加载。另一个错误就是把太多技能设成全局。我越会和智能体共事，就越发现自己在写越来越多的项目专用技能。原因很简单：你在一个具体项目里工作时，工作流通常也是对该项目专用的。这听起来像废话，但即便是「代码审查」这种看起来很通用的技能，从一个仓库审到另一个仓库，做法也可能略有不同。

所以与其只有一个笼统的代码审查技能，你也可以为每个主要仓库各写两三个专用的，它们会更有效，因为更熟悉那份代码。项目技能就是这个意思。新手会把一切都做成全局技能，所有东西搅成一团，时刻全部加载，既浪费 token，也让智能体糊涂。真正进阶、懂得怎么用技能的人，当然也会有一些全局技能，但大多数技能放在项目里，针对那个仓库、那份代码，高度相关，因而更有效。

而且你在做别的事情时，它们不会被加载，也就不会浪费 token 或用量额度。这对团队几乎是必需的。听好：如果你手下有团队，一定要理解这一点。团队里通常有一个人最懂某一项任务，是这件事上的专家。公司大一点，可能是最懂市场的市场总监，或最懂财务的财务总监。无论是什么，团队里通常有一个在某件事上最强的人，而这个人可以写一个技能。

如果你们做得对，是一家 AI 原生、真正按 AI 来构建的公司，就该和团队一起，按特定主题建立共享的 GitHub 仓库。可能是招聘，可能是会计、财务、投资，可能是产品开发。这些仓库哪怕和软件开发、写代码毫无关系，也该聚焦于生意的不同领域，用来存放工作文件、不同的知识和上下文，替代 Google Drive，替代 OneDrive、Microsoft Teams，替代 Dropbox、Box 这些存储方案，也替代很多人用来干这件事的 Notion。

我觉得这是更好的方案：就是为这些事建立 GitHub 仓库。你有这些专门的 GitHub 仓库，它们就该拥有专门的技能。我们已经讲过让技能保持专门有多重要。美妙之处在于：如果由团队里最强的那个人来写，并推上去，团队里每个人都会得到来自最强者的技能。当你在那个仓库里和智能体一起工作时，智能体就会用到团队里最会写的那些技能。就这样，你能把最强的人变成对所有人的杠杆。

最好的视频剪辑、最好的缩略图设计、最好的平面、最会找客户、最会做销售——公司里在那件事上绝对精通的人，可以写下几个技能，讲他如何和智能体一起做那件事。

然后，如果一个新实习生进来并得到那个仓库的权限，他的智能体也就拥有了那些技能。于是这个实习生不再是完全派不上用场、要花几个月才能跟上的人，而可能在一周内跟上，因为他拥有公司里最强的那个人写下的全部专门技能。

所以，如果你有团队，绝对该把内部工作组织成这样。这非常强，能给团队里每个人加上很多杠杆，提升所有人的生产率，也能防止一些你过去犯过、不愿让更初级的人再犯的蠢错误。只要写一两个技能，放进那些 GitHub 仓库，那些人下次在那里工作时甚至不会知道技能被调用过，只是彻底避开了那个错误。
