一句话概述

Anthropic 平台工程负责人凯特琳·莱斯（Katelyn Lesse）对格尔盖伊·奥罗斯（Gergely Orosz）讲述：一个小团队如何用五个月把服务每一个 Claude token 的 API 从 Python 单体改写成 Rust，又如何用影子流量和「可验证」来代替深读智能体写下的大部分代码。团队仍是大约五到十人的「两个披萨」编制，编程面试在逐步退出，产品经理会把代码推到生产环境；她也谈到工程师的身份认同危机，以及为什么安全、认证和基础设施仍然需要人先做对。

核心要点

  • Claude API 最初是跑在谷歌云单一区域的 Python 单体；流量上来后 CPU 不够用。语言选择来自约三年前研究公司起步、团队与研究交叉、当时研究社区主要用 Python，而不是一开始就忽视性能。
  • 重写大约花了五个月。她给出的原因很具体：Python 太吃 CPU，出现了 CPU 短缺，而且模型已经非常擅长写 Rust。验证靠影子流量对比行为差异，而不是人去逐行审全新实现。
  • 智能体开出的拉取请求里，团队大概不会深读约 80%，约 20% 才会仔细看细节。前提是把行为做成可验证的。代码审查和值班都在往这个方向改，Claude 被接进内部系统后还可以参与排障。
  • 新人认识系统的方式变了：Python 系统本来就没有完美文档，现在很多人一来就问内部 Claude，拿到可点击的交互式说明，而不是只靠白板上的方框箭头。
  • 组织上仍是大约五到十人的两个披萨团队，人对系统负责。编程面试在「逐步退出」，改试智能体驱动的面试；职级和晋升还在，但招聘更偏资深。产品经理会把代码推到生产环境，她和主持人都指出这与大多数公司不同。
  • 面对身份危机，她把乐观放在更大的问题上，例如用持久化智能体去准备药监申报材料；但若安全、基础设施和认证没先做对，多智能体团队解决不了那些大问题。她推荐《项目哈雷彗星》，理由是「不会沟通的双方必须想办法合作」，和此刻与人工智能相处有对照。

值得看 / 可跳过

值得看：这是少有的、把 Anthropic 平台工程从 Python 到 Rust、影子流量、代码审查比例、面试和职级一路讲到可操作细节的长访谈，约 1 小时 50 分钟，对做平台、智能体工程或招聘的人信息密度很高。可跳过：只想听模型能力发布、不关心工程组织和迁移的人；开场和约 28 分有 Entire、Antithesis、turbopuffer 口播，可跳过。若已读过《Pragmatic Engineer》那篇 Anthropic 深潜，后半关于身份认同的讨论仍有新的例子，但会有部分重复。

  1. 1冷开场：八成智能体拉取请求不必深读，编程面试也在退出查看原文 →

    冷开场里，凯特琳·莱斯（Katelyn Lesse）说他们刚用 Rust 把整层 API 重写了一遍。关键不在于人去盯每一行 Rust：只要把事情做到「可以验证」，就不必审阅智能体写下的每一行。她估计，团队大概不会深读智能体开出的约 80% 的拉取请求（pull request）；编程面试也已经在产品和平台团队里逐步退出。有人可能过不了传统写代码面试，却能在其余环节表现极好，因为他们已经不再一直手写代码。主持人点出软件工程师的身份认同危机：最难受的，往往是过去把自己定义成「敲键盘、写代码、事情就做完了」的人。节目介绍里，凯特琳是 Anthropic 平台工程负责人，她的团队拥有服务每一个 Claude token 的 API，以及 Claude Code、Claude Desktop 背后的基础设施。本集将谈到一个小团队如何用五个月把整层 API 从 Python 改写成 Rust、代码审查被什么取代，以及她对不再手写代码的工程师有什么建议。

    进入正题前，主持人先问她如何对计算机和科技产生兴趣。她随后谈到在 Betterment 的经历，以及为什么最终去了 Stripe：更早以前她就关注 Stripe 在支付边缘做新金融产品，而且主要在纽约推进，当时她本人也在纽约；真正加入，部分是因为一位她很喜欢的 Betterment 经理已经过去。她在 Stripe 做的是贷款业务 Stripe Capital。主持人记得那时 Stripe 的工程文化开始在外部出名，尤其在金融科技里，很少有公司会让人联想到如此高的工程标准。她同意这一点：Stripe 是一个可以做出色工程、行动快、也允许野心的地方，是工程主导的文化，扩展新业务的速度很快，也兑现了她此前的期待。这段为后面对比 Anthropic 如何组织工程团队做了铺垫。

  3. 3Claude API 怎么跑：无状态对话，以及把整段会话状态来回传递查看原文 →

    主持人把话题转到 Claude API 本身如何工作。凯特琳解释，这条 API 在形态上很特别：聊天本质上是无状态的，因此每一次模型回合都要把整段会话状态来回传递，他们后来做了一些工作让这套机制更稳，但运行形状仍然独特。这为后面的重写提供了背景——服务的不是普通的请求响应，而是高流量、高状态搬运的推理入口，也是 Claude Code 和 Claude Desktop 背后的同一层基础设施。

  4. 4五个月把 Python 单体从单区域改写成 Rust：不是一开始就选错语言查看原文 →

    API 最初是用 Python 写的单体，而且跑在谷歌云（GCP）的单一区域里——「很早以前」，但其实也没那么久。请求量飙升之后，单是集群里的 CPU 就开始不够用。主持人不解：Anthropic 一直招世界级工程师，为何一开始用性能常被瞧不起的 Python？凯特琳说这发生在她加入之前，大约三年或更早：当时 Anthropic 还是一家做模型的研究公司，并没有对外提供模型服务；决定做 API 和产品时，团队很小，而且与研究交叉，研究社区当时主要用 Python，所以就从那里起步。重写花了大约五个月，由一个小团队完成。她在节目后段和主持人的收束里也点明原因：Python 太吃 CPU，出现了 CPU 短缺，而模型已经非常擅长写 Rust。验证策略的核心是：只要能把行为变成可验证的，就不必人工审每一行新代码。

  5. 5用影子流量验证重写：八成不必深读，两成才值得盯细节查看原文 →

    重写不是靠人把新旧两套实现逐行对比，而是用影子流量（shadow traffic）去看行为差异和错误。她举例：有一次一个功能在 Python 系统里从测试直接进入正式发布，Rust 团队没有料到，影子流量突然冒出大量差异和报错，他们才发现是新功能已全面放开；此后又补上了检查和流程。回到代码审查，她再次给出那组比例：智能体开出的拉取请求里，团队大概不会深读约 80%，真正需要盯细节、判断该修什么的大约是 20%。前提仍然是「可验证」——有可靠方法确认每一行该不该过，而不是回到人工读完整份 diff。中段之后进入赞助口播，再回到新人如何认识这套已由智能体大量参与写成的系统。

  6. 6新人怎么认识一套智能体写出来的系统：直接问 Claude查看原文 →

    旧系统由人手写时，通常有几位待得久的工程师摸清整体结构，好一点的团队还有文档，尽管文档会过时。新系统改变了这一点。Anthropic 大约三年前才有 API，团队和负载都涨得极快，Python 系统并没有完美文档，所以重写也不能「按文档照着做」。在很大程度上，代码本身就是给智能体看的文档。系统设计层面则变化更大：以前新人要找人一起上白板画方框和箭头，或去翻可能过时的示意图；现在很多人一来就问 Claude「这套系统怎么工作」，常常得到可点击的交互式应用，而不只是静态框图，也可以要散文、视频或播客风格的讲解，按自己习惯的方式学习。主持人点出前提：这不是对外那个 Claude，而是已经接上代码库、可观测性、复盘等内部数据的内部实例，才能检索和利用这些材料。

  7. 7打造 Claude 托管智能体：让智能体真正在公司内部跑起来查看原文 →

    话题转到构建 Claude 托管智能体（Claude Managed Agents）。重点不再只是单次对话里写出代码，而是让智能体在真实的内部环境里持续工作：连上代码、工具和权限，处理更长周期的任务。凯特琳从平台工程的角度谈所有权——API 层、运行环境和产品表面如何接在一起——以及为什么「能验证」仍然是放手让智能体自动干活的前提。这一段也为后面的团队结构做准备：智能体可以承担更多实现，但系统的责任仍落在人身上。

  8. 8两个披萨的团队还在，智能体可以独立做完哪些事查看原文 →

    她认为团队形态与人工智能之前并没有那么不同：现在仍然大致按「两个披萨」的团队来运转，有的稍大一点，大约五到十人；这个人数仍然适合让一组人真正理解并承担一套系统。变化在于智能体可以独立完成的工作变多了，尤其当任务能被验证时。但责任没有消失：改动可能从许多路径进来，仍需要一组理解系统的人对结果负责。这解释了为什么他们没有因为智能体写代码就拆掉小团队结构。

  9. 9人还怎么做代码审查，以及和 Claude 一起值班查看原文 →

    既然八成由智能体开出的拉取请求不会被深读，人的代码审查就集中在那需要判断的大约两成，以及审查本身是否仍然提供独特信号。值班（on-call）同样在变：Claude 被接进内部系统后，可以参与排障和理解系统，而不是只在聊天窗口里答概念题。主持人后来也对照 OpenAI 用 Codex 做入职的说法：两家都会把几乎所有系统接到内部的 Claude 或 Codex 实例上，智能体因此比大多数公司里的智能体拥有多得多的上下文——这也是一项需要谨慎处理权限和知识产权的工程选择。

  10. 10产品经理也能把代码推到生产环境查看原文 →

    一个让主持人有些意外的事实是：Anthropic 的产品经理会把代码推到生产环境。他指出，大多数公司里生产代码仍由工程师负责；Anthropic 的产品经理往往非常技术化，不少人来自工程背景，所以他怀疑这件事会不会在别处同样普遍，但认为值得记下。这段也和前面「验证先于手写」的主题相连：当测试、门禁和智能体工作流足够强，谁按下发布，不再只取决于是不是传统意义上的工程师，但仍要有人对系统负责。两个披萨的小团队再次被提起，作为「总有一组人理解并承担这套系统」的组织答案。

  11. 11软件工厂，以及为何逐步退出传统编程面试查看原文 →

    谈到 Anthropic 的「软件工厂」时，重点是规格、验证和生产轨迹如何闭环，而不是简单用智能体替代工程师。招聘上，他们特意说自己是在「逐步退出」而不是立刻删掉编程面试：过去编程面试一直和技术设计、过往大型项目讨论等环节并行；现在越来越常见的是，有人过不了上机写代码，却能在其他环节表现极好，因为他们已经很少手写代码。他们开始试验由编程智能体驱动的面试：审查智能体写的代码、审查智能体做的系统设计，或用编程智能体去搭建一个系统，目的是测量一个人能否真正用这些工具把事情做完。主持人提醒，传统编程面试在大公司里方便，有两个原因：题目即使泄露也仍有一定信号，以及容易训练大批面试官打出大致可比的分。凯特琳同意面试从来都不完美，成功与否不只取决于想测什么信号，还包括能不能信任它、团队打分有多费劲、量表能不能减少偏差。所以他们不是直接删掉编程面试，而是同时寻找可扩展、可打分的替代方案。

  12. 12职级仍在但更偏资深，身份危机，以及推荐《项目哈雷彗星》查看原文 →

    入职之后，职级、晋升和绩效评估都还在做，两件最不同的事之一是招聘明显更偏资深。职级和晋升对职业生涯仍然重要，但过去在初级档位更确定、更好量化的部分已经变了。谈到身份认同时，凯特琳说：如果快乐来自攻克有野心的问题，眼前未解的问题几乎是无限的；更难受的是那些把自己定义成「敲键盘写代码、事情就完成了」的人。她想点燃的乐观是：人也许不再写每一行代码，但目标是让疾病被治愈、让机械等领域里从前像科幻的事发生。有人会说「这有什么关系，智能体迟早会做」；她的反驳是，要想让智能体解决那些大问题，必须先解决安全、基础设施、身份和认证等工程问题。她举制药为例：客户开始做几乎像甘特图一样的系统，由持久化智能体接力准备提交给美国食品药品监督管理局（FDA）的材料，很多环节也许不必人人在回路里——但这只有在底层工程做对之后才不会先出「坏问题」。主持人提醒，多智能体对只有 Max 订阅档的普通工程师可能还很遥远；她的建议是先提高野心，同时跟着智能体把安全、可靠性或自己的领域学深，预判以后会更复杂的问题。她推荐最近读得开心的书是安迪·威尔（Andy Weir）的《项目哈雷彗星》（Project Hail Mary），电影也不错：一个人类和一个外星生命必须在不会沟通的情况下想办法合作，让她觉得和此刻与人工智能相处有某种可对照之处。收束时主持人再次概括 Rust 重写的原因：Python 太吃 CPU，出现了 CPU 短缺，而模型已经非常擅长写 Rust。
